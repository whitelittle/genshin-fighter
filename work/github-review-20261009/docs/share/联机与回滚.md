# 联机与回滚

## 身份和状态归属

区分稳定 GUID、运行时实体、列表序号与 UI 模板索引。事件挂载对象的“自身实体”不能未经实测当作发送玩家。把信号来源端口、实际玩家实体列表和目标玩家输出打印在同一行核对。

列表从 0 还是 1 开始取值应以平台实测为准。共享控制对象保存双方实体与会话状态，客户端各自持有席位。UI 图片索引不能用于玩家路由。

## 握手和菜单同步

流程为席位请求 → 席位回包 → 选择/准备快照 → 双方资源加载完成 → 开战请求/回包。席位回包成功不等于可以战斗，人数达到二也不等于双方准备完成。

快照附会话代次 Epoch 和递增 Revision。旧代次丢弃；旧修订丢弃；相同修订可重发回包用于修复丢包。新代次清除双方准备、加载状态及上一场输入缓存。单调版本号比一次性的永久 Started 开关更适合重赛和多回合。

准备至少区分选择中、锁定但加载中、加载完成、退出。地图/场次/比分由指定权威端产生，另一端跟随，不能各自随机。退出和重选要有持续可重发状态，不能仅依赖一次瞬时事件。

## 输入转发与回滚

输入消息附发送席位、首帧、确认帧、负载和会话代次。服务端原样转发给另一位玩家；不要漏掉负载或确认参数。静止也要发送空输入和 ACK，否则远端会误认为未来输入一直缺失。

确认落后达到预测窗口时暂停预测，等待后继续。其目的是限制错误预测积累，不表示每次攻击都应等服务器逐招确认。命中停顿是战斗规则，回滚是纠正过往预测，两者应单独计数。

快照包含会影响后续模拟的一切状态：位置、速度、血量、能量、动作时间、连段、标记/护盾/增益、随机种子、回合/胜场。UI 控件、渲染缓存不进入逻辑快照，纠正后从最终状态刷新。

## 故障定位

依次看席位回包、开战回包、发送/收到输入、网络帧、远端确认、对方确认、回滚与重演次数。发送不断增加但收到为零，先检查服务端路由/信号参数；双方收到增加但确认落后，检查 ACK 与帧序；逻辑收敛但画面延后，检查渲染与加载成本。

日志按阶段合并一行，包含信号、代次、席位、来源、目标、关键参数。不要每帧打印完整负载。冻结、帧差和画面差需要结合双方同步录像核验，单张截图不能证实一秒网络延迟的成因。

本地模拟信号与分支不等于已生成官方节点图。节点导出修改必须先核验文件格式、节点类型、参数类型、连接端口、变量归属及导入结果；保留原文件。
