# 第一版分段加载实现说明

这是实现记录与模拟器证据，不是手机性能承诺。2026-10-03，构建入口 `work/build-test-v1.mjs` → `work/build-duel-loading.mjs`，菜单源 `work/test-v1-menu.lua`，加载源 `work/test-v1-loading.lua`。

## 改动

旧加载候选运行时创建9,275张图片；新完整菜单只创建1,214张动态图片。控件模板还有静态场景、按钮、文字、卡片头像和派蒙，最终静态控件1,132个。动态每张图片由一个模板容器和一个Pixel组成，所以动态控件数是图片数约两倍，不能把图片数等同总控件数。

预览共用两份504容量的Sprite池，头像各103容量。战斗创建当前角色上限与504之间的差额，迪卢克额外火鸟338。返回时用 `game.DestroyClientUIControl` 销毁模板容器，删除注册表条目、释放角色姿势展开表，保留菜单所需前缀。下一回合同角色复用，未来接力应在下一位上场前重走黑屏加载。

9名新角色的20状态名中，12幅独立姿势与8个复用引用分别记录；复用姿势数据只存一份。每行坐标/尺寸用字节十六进制、颜色用逐帧调色板索引，整块存为字符串。全部紧凑源数据随Lua读取；未选角色不展开成数千个行表。进入战斗时按约2ms时间预算分批展开所选角色。并非外部资源下载。

原多色大图背景没有增加采样分辨率，而是移除其运行时图片池，换成原生矩形/圆形分层与统一透视铺地。避免用“提高背景清晰度”把常驻池再推高。

## 生命周期与同步

加载器占用OnInit/Start/Update，先完成小菜单，再启动游戏原生命周期；后续加载时暂停客户端模拟入口，保留已注册的信号处理器。准备状态区分未准备/已确认/加载完成，双方加载完成才能Join。Join/Joined都带Epoch，旧回包不能开启新会话。

加载时仍绘制派蒙、真实工作进度；原脚本初始化或启动报错会保留黑屏错误文字。一次最多24次实例创建或256行数据展开，仍受时间预算约束。它们是工作上限，不能推断各手机实际速度。

返回/重新选人以Flow传达，并在快照中保留返回状态，处理快照和退出包不同先后顺序。双方再战才新建回滚会话。同场景/角色的资源不重复创建；过期Epoch输入与Joined回包忽略。

## 测量边界

完整候选GIA约3.04MB，Lua约2.1MB；未压紧的11角色中间候选GIA约6.64MB。这里比较的是同一新版本的构建大小，不代表本次真机加载时间缩短到原来的相同比例。

已有模拟器验证：首次菜单、仅一方准备、双方战斗、返回释放、重进；11角色入口；结算单方再战等待/双方再战；三手机比例；原防御/浮空/延迟丢包回滚收敛；部分新特性。尚未获得本版手机加载时间/帧耗时。攻击卡顿若诊断显示远端确认落后，仍要检查空输入/ACK持续转发，而不是只调整图元池。
