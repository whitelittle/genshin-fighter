|变量|类型|初值|
|---|---|---|
|P1、P2|实体|无初始值|
|Epoch、Stage、Round|整数|1|
|Wins1、Wins2|整数|0|
|P1Revision、P2Revision|整数|-1|

Stage为本版七背景中三张有序选择的种子，合法范围1～210；不是场景实体ID。旧版Stage=0曾能运行，不说明本版范围检查也接受0。Ready：0未准备、1锁定、2资源就绪、3首页状态；角色0未选择、1～19有效。Revision从客户端0开始，服务器-1才能接受首次0。旧P1Assigned、P2Assigned、Started、IsInit不在本版17变量中，无需为本版新增；旧变量先保留，不因未被新图引用就擅自删除。

## 执行分支

1. Hello：列表长度至少1时，保存P1并直接向列表[0]发送Slot1；至少2时保存P2并向列表[1]发送Slot2。回包目标直接用列表项，保留变量供后续路由。重复Hello允许重新发席位，不用永久IsInit挡重试。
2. Team：先校验Slot、角色、Ready、Stage、Round、Wins、Epoch及Revision范围。锁定/就绪必须三人完整且互不重复。旧Epoch丢弃；新Epoch重置双方Ready及Revision，再保存本席位信息。旧Revision丢弃，相同Revision可重发。场景/轮次/比分以P1为准，P2不得覆盖。保存后向双方发TeamOut。
3. Join：至少两人在场、Epoch一致且双方Ready=2才向双方发Joined。可重复确认。加载未完成不是已经开战；本版不依赖Started变量。
4. Frames：Epoch一致且双方Ready=2，Slot1转P2、Slot2转P1。Payload原样透传，不拆、不加前缀，不按到达顺序删旧帧；客户端负责乱序、回滚和确认。
5. Flow：合法Slot/Action/Epoch/Revision；Action1重赛要求当前Epoch，Action2退出和3返回选人允许通知跨更新顺序，由客户端进行相邻Epoch及Revision过滤。不能简单让所有Flow都要求完全相同Epoch，否则可能漏退出通知。

当前三人分别用于ROUND1/2/3，三局两胜；不是场内三人接力。

## GIA格式踩坑

- 使用官方导出样例确定节点、特化、端口和信号内部ID，不根据截图猜数字。信号必须实际被监听/发送节点引用，才可作为导出样例证据。
- 保留未知protobuf字段、头部长度、尾标记；输入引用上游数据输出，执行出口引用下游入口。镜像连接和自定义端口ID必须一致，官方再导出可能省略部分可选镜像字段。
- 整数直接型为literal.102，泛型为literal.110.2.102，不能两条同时填。非零已填写整数需要字面量状态field2=1。负数用有符号32位解码，避免先转Number损失精度。
- 本次旧生成器同时填两条路径或漏状态，导致导入后列表索引、Slot、范围上限和Revision重置清零。修复涉及21处值/状态，不能只手改三个席位数字。
- 导入信号可能重命名。本次样例4显示名称映射变化；样例5证明引用现有信号方案保留名称、资源ID及修正整数。样例5本地逻辑通过时，用户仍报告等待席位，因此不能认定结构通过等于真机通路成功。
- 当前整套带定义，便于重装；先前无附件定义方案仅用于同关卡已有资源，不是独立重装包。图的名字正确不能证明客户端脚本或信号绑定正确。
