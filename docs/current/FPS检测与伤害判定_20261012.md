# FPS检测与伤害判定

## 程序

战斗界面左侧血条、能量条下方显示FPS、当前采样窗最大回调间隔和累计丢弃时间，大招和暂停时仍可查看。FPS按原始OnUpdate dt累计，约每秒更新，定义为回调次数／累计秒数；不是GPU实际呈现帧率。只复用少量gf_ui图元与一个文字槽，GF_FPS_VISIBLE=false可隐藏。最大间隔按采样窗统计，丢时为应用运行累计，包含超过250ms的截断及积压上限裁切。旧版漏记250ms以上截断，本批补齐诊断计数，模拟调度规则不变。

伤害由gf_sim及其战斗模块计算，与图片切片、动画显示帧和图元池独立。普通攻击在startup至startup+active期间，用角色位置、朝向和招式矩形计算攻击框，与姿态受击框做矩形重叠。S:hit先检查无敌、倒地／起身／KO／被投状态，再判断防御方向、上下段、霸体、连段修正、元素反应和护盾，最后扣血及设置硬直、击退／浮空、命中停顿等。命中或格挡后connected=true，阻止同一段普通攻击每拍重复命中；多段招式按自身指定逻辑时点执行。

芙宁娜和绫华大招在第12逻辑拍检查前方距离、高度、防御及受击状态；确认后进入锁定演出，再分别在56／78／100与70／94／118拍结算三段伤害。确认后的不可防御／忽略无敌为既有演出规则，不是所有攻击都绕过保护。投技和持续伤害有独立时点逻辑，不能把全部伤害概括为普通攻击框。

保险机制包括固定60Hz整数逻辑、逐拍补算、普通攻击connected、防御／无敌状态、血量和能量边界、联机快照回滚及确认事件处理、失同步／断线结束对局。它们保护已有规则，不能保证任意卡顿都完全不影响体验。

每次回调最多补4拍，并保留最多4拍积压；单次dt上限250ms。持续低于约15回调／秒或长时间阻塞时会丢时，战斗可能比现实时间慢。不会按FPS比例缩减每次命中伤害，也不会因没有绘制某一动画帧跳过仍被执行的判定拍；短于输入采样间隔的按键可能漏采。联机等待及预测上限也可能使逻辑暂缓，不能仅凭FPS推断网络或判定问题。

## 模拟器验证

runtime/tests/fps_monitor.py在生产96文字池下验证显示和训练暂停展开出招表。以同一芙宁娜大招输入在60／30／15次回调每秒各运行3秒，均执行180逻辑拍，实际伤害大于0，伤害、HP及状态哈希相同。验证30回调FPS计算和500ms原始间隔、截断丢时计数。旧双角色3600拍全状态差分、349像素状态、桌面及手机横竖屏全流程和双端回滚检查通过。模拟器频率不是测得的真机FPS。

## 真机待验证

匿名玩家要求加入真机FPS检测。已生成检测版脚本GIA；真机需要导入仅脚本GIA，替换GF_HOST旧脚本并保持唯一主脚本。继承16000池、672／672／656三段扩池、模板索引1073741845及宽屏修复。

观察待机、E、两人分别Q、连续多局时的FPS与max间隔，以及丢时是否增长。若丢时持续增加说明逻辑调度已触及保护上限；若FPS稳定但操作或画面顿挫，还须结合联机等待及原生呈现排查。本批没有直接连接或测量手机，不登记真机性能验收。
