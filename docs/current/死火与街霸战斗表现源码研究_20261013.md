## 状态与结论

**源码静态核验**：已读取两边的核心动作、命中、受击、防御、连段、投技和效果调用链，建立外围系统定位索引；不是逐角色、逐招式、逐素材穷尽审阅。本文每处源码结论给出文件与函数，完整固定提交链接见[定位索引](战斗源码定位索引_20261013.md)。

**设计建议**：本项目适合吸收死火的角色专属技能编排，以及街霸的判定和交互精度。华丽程度与格斗严谨性可以一起提升：特效负责解释招式，判定、停顿和受击负责让玩家知道发生了什么。

**模拟器验证**：本批未运行两个参考游戏，也未运行新战斗方案。仅进行源码下载完整性、固定提交与文档定位校验。

**真机观察**：本批无新增观察；不推断真机手感、帧率或美术验收。

**待验证推断**：本文的改进优先级与方案是研究建议，未改变当前六角色稳定版，未改角色动作设计、数值、素材、Lua或联机协议。

## 整体调用链

死火沿 `FighterKeyCtrl → FighterActionLogic → FighterMcCtrler / 地面、空中Handler → FighterMC` 处理输入和动作。当前姿态查找身体区域、命中区域，`GameMainLogicCtrl`取得双方判定后调用`beHit / hit`。受击控制器选普通受击、防御或刚体分支，效果系统再处理火花、声音、冻结、镜头与慢放。技能可以通过事件生成`Bullet`、`FighterAttacker`和跟随效果。

街霸沿 `CMD_MAIN`识别指令，角色主状态及`PLPAT / 角色专属PLPATxx`推进动作，`CHARSET`读取当前动画数据与判定索引。`HITCHECK`先收集、比较和裁定结果，之后进入角色与角色、角色与效果、效果与效果的处理；防御、受击和Parry分开。`EFF02`组织命中火花、声音、方向、颜色与震动。

共同的启示是：动画不是孤立的图片播放。一个动作还包含位移、判定生效、可接招的窗口、命中结果分支、受击反馈与结束清理。

## 已核验的核心实现

### 1. 动作时间轴同时编排身体、事件和判定

死火的`FighterMcCtrler`给时间轴提供`setAttack`、`setSkill1/2`、空中动作、必杀、`move / damping`、`fire / addAttacker`、`moveTarget`等接口。`FighterMC.renderAnimate`推进主动画与子件，再查身体和攻击区域。`FighterAction`保存此刻开放的后续动作。连招许可因此可以由当前时间轴阶段改变，完整角色招式还依赖未下载的FLA/XFL帧脚本。

街霸`CHARSET.char_move`解释动画表中的控制记录，`check_cgd_patdat2`解析当前姿态的攻击、判定、声音及层级等字段，`set_jugde_area`切换身体、手部、攻击、抓取和被抓取的数据入口。`PLPAT.Player_attack`负责共用攻击状态，并通过角色专属表分发特殊招式。

**设计建议**：把用户给出的动作接成明确时间线，每个阶段都知道身体姿态、脚底/握点、世界位移、判定和特效事件；保留角色自己的数据和编排。统一的是执行约定，不必把所有角色招式强行变成同一个模版。

### 2. 判定和接触位置决定反馈落在哪里

死火`GameMainLogicCtrl`将身体推挤与攻击检测分开。攻击取得双方当前命中区域与身体矩形，先算双方交集，再分别调用命中和受击。身体推挤按重量及是否顶到边界分配位移。当前版本的攻击细测受`_renderAnimate`门控制；`GameConfig`默认逻辑60、动画30，不能把动画拍直接当作本项目60Hz模拟拍。

街霸`HITCHECK.attack_hit_check`分别遍历攻击区域与多个受击区域，排除无效框、同属对象和其他不允许组合，再用镜像后的世界矩形判断。命中结果先入队，再由`set_judge_result`处理。`HITPLPL`对同拍交互进一步按攻击属性处理，不能仅按检测先后决定谁赢。

死火`EffectHitHandler`取相交矩形中心放火花。街霸`cal_hit_mark_position`也计算交集中心，另有`cal_hit_mark_pos`支持招式指定位置补正。

**设计建议**：默认火花落在真实接触点，刀尖、枪头或演出定点允许明示覆盖。显示框、攻击框、受击框、身体推挤框分开；调试页应同时显示。超长刀光或水束的外框不应改变人体大小。

### 3. 防御、命中和霸体具有不同结果

死火`FighterKeyCtrl.defense`是下键防御；受击控制器根据防御状态、方向、破防抓取等条件选择分支。`doDefenseHit`削血、消耗体力、限制防御硬直并施加推退；体力不足进入`doBreakDefense`。`doSteelHurt`有普通与超级刚体分支，受到不同伤害比例并消耗资源，特定攻击可打破普通刚体。以上不能直接解读为街霸式“后方向＋上/下段”防御。

街霸`plef_at_vs_player_damage_union`明确分地面/空中、Parry、防御和受击。`defense_ground / defense_sky`读取攻击防御属性、方向与角色状态。`set_guard_status`和`set_paring_status`有各自的停顿、能量及动作状态处理。这里只核验这些分支，不把PS2配置项自动当作默认街机规则。

**设计建议**：我们可以保留当前后方向防御和上/下段规则，同时让普通防住、霸体承受、护盾吸收、无敌穿过分别有不同的声音、火花和姿态。破防、Parry、受击脱身是否加入属于新的系统设计决定，不因找到代码就全部启用。

### 4. 停顿是规则的一部分，慢放是另一个机制

死火`EffectCtrl.doEffectVO`从效果数据触发冻结、震动、闪光和慢放；`freeze`将毫秒转为逻辑拍并调用游戏暂停，效果控制器仍负责倒计时。`EffectSlowHandler`通过动画刷新间隔和游戏慢速率控制慢放。因此命中特效配置可能影响游戏推进，并非纯画面参数。

街霸`PLMAIN.check_hit_stop`分别处理自身命中停顿和受击停顿，包括特殊符号语义、相互覆盖及超必杀冻结状态。`set_paring_status`还给双方不同的计时结果。`SLOWF`用`EXE_flag`控制慢放时的执行节奏，结局慢放有专门入口。

**设计建议**：本项目继续由确定性模拟管理停顿和技能锁定；特效数量、画质与手机掉帧不得影响停顿拍数、取消许可或伤害事件。需要分别定义：双方命中停顿、仅目标锁定、全局必杀冻结、纯视觉慢放。降级时保留接触帧与关键受击姿，优先减背景装饰和残影数量。

### 5. 连招分为输入记忆、取消许可和命中结果

死火`FighterKeyCtrl`区分保持与刚按下，使用方向＋攻击/技能/必杀键的组合；`FighterMcCtrler`开放或关闭各后续动作。`justHitToPlay`通过攻击ID确认对手的受击记录，可选是否包含防御，随后跳到指定帧标签。它是明确的命中分支接口，不能仅根据当前有无火花判断连招。

街霸`CMD_MAIN`按角色指令表推进识别状态，成功后设置招式有效计数，再逐拍递减。`PLS03`另检查资源、空地、招式权限和输入，包含连打取消、目押相关检查、必杀与超必杀入口。存在角色与招式专用条件，不能用一句“任何普通攻击都可以接大招”概括。

**设计建议**：后续动作的数据应明确：何时接、能接谁、打中/防住/打空是否允许、消耗什么资源、输入记忆能保留多久，以及停顿期间是否接受输入。不要仅凭动画播到末尾让所有招式顺序播放。传统目押连段与主动取消连段也要区别：前者依赖收招结束后的时序和距离，后者改变当前动作。

### 6. 多段攻击必须有命中身份与重复限制

死火普通受击设置`isAllowBeHit=false`及`_beHitGap`，子弹另有`hitTimes`和寿命，命中后还能变速。街霸`CHARSET.set_new_attnum`在新攻击段更新`attack_num / att_hit_ok`等状态；判定成功会消耗当前攻击许可，后续攻击段才重新开启。

**设计建议**：一个技能可以有很多视觉闪烁，但伤害只由明确攻击段触发。为每段提供唯一段号、单目标命中记录、可重复间隔和结束条件。技能的持续光束、伙伴与召唤物要有独立所属方和生命周期；镜像与换人不能改变所有权。

### 7. 受击链塑造重量和连段节奏

死火`HitVO`包含水平/垂直冲量、受击时长、受击类型及重力开关。`doHurtAnimate`区分空地、普通僵直与击飞，打断当前动作和相关效果，再推进受击姿态。`GameConfig`另有落地阻尼、反弹范围、倒地时长和起身参数。被打脱身、倒地跳起有资源及累计伤害等限制。

街霸根据受击部位、蹲站和空地选择伤害反应，在`PLPDM`处理飞行、落地、硬直及伤害。`PLMAIN.look_after_timers`维护受身和拆投窗口。浮空可追击的全部例外和每个角色的反弹细节，本批没有穷尽核验。

**设计建议**：基础受击至少应表达轻重、空地、击退方向、倒地和恢复，脚底与人体比例不能跳变。强击应有明确接触停顿→受击加速→飞行/滑行→落地→起身链。冲量、重力和动画切换分开，避免受击图片本身的外框改变物理。

### 8. 连击计数和伤害限制必须反映真实交互

死火`FighterEventCtrl`在命中事件里增加连击，并在目标恢复等事件中清除；`GameLogic`保存攻击方、受击方与UI归属。这里只确认计数链，没有证据可宣称它采用街霸同类的连段伤害衰减。

街霸`add_combo_work`记录攻击种类及次数，`cal_combo_waribiki`根据既有连段组成、对应权重与倍率表计算伤害衰减，眩晕另有`cal_combo_waribiki2`。它不是简单地每多一次命中固定减一个百分比。

**设计建议**：连击结束条件由对方是否恢复可行动决定，演出多闪几次不增加连击。衰减、受身机会、浮空上限、距离脱落共同约束长连段；不要只依靠最终强制无敌兜底，也不先照搬一整套商业游戏公式。

### 9. 投技需要双方演出和失败分支

死火`FighterMcFloorHandler.doCatch / allowCatch`结合目标状态与范围决定抓取；`moveTarget`允许通过指定位置或角色子件锚点移动目标。街霸`PLPCA.Player_catch`和`PLPCU`分别处理投与被投，`check_nagenuke`读取拆投计时、状态与输入后同时改写双方状态。

**设计建议**：投方和受方共用一条配对时间线，记录握点、双方root、接触、伤害、释放和落地；投空、拆投与不可投状态独立定义。墙边、双方同角色、体型不同和换向都要能复现，不能把受方图片临时贴在投方特效上。

### 10. 华丽技能来自对象协作与阶段切换

死火将角色身体、`Bullet`飞行物、`FighterAttacker`独立攻击物、`Assister`辅助与`FollowEffectView`跟随效果分别管理。`BaseFighterEventCtrl`保存所有者和队伍，跟随效果可放身体前后。子弹有寿命、攻击次数、命中变速和被其他攻击破坏的路径，远程招式因此可以离开身体动作继续运行。

街霸`HITCHECK.set_struck_status`分派角色/效果组合，`HITEFPL / HITPLEF / HITEFEF`为独立对象交互提供入口；`EFFECT / EFFxx`包含大量招式对象与演出对象。单靠`EFF`文件名不能判定其是否纯视觉，必须查有无命中队列与攻击属性。

**设计建议**：角色身后残影、剑迹与装饰光属于视觉；波、柱、伙伴攻击等在需要碰撞时才建立独立规则对象。技能分起手预告、有效阶段、命中分支和收势，特效阶段跟随这些事件。华丽程度主要来自组合和节奏，不是常驻铺满画面。

### 11. 火花、声音、镜头应由同一结果解释

死火`EffectHitHandler / EffectManager`依据命中类型、目标与专属覆盖选效果；`EffectVO`同时组织动画、声音、冻结、闪光与震动。`FighterEffectCtrl`提供挥招环境、脚步、落地、冲刺、残影、必杀立绘与暗场；角色语音控制器限制同角色的语音通道重叠。

街霸`EFF02.effect_02_move`从`HMDT`选命中/防御火花、声音、颜色、方向和震动表；`CHARSET`另有动画帧声音字段和层级优先参数。命中火花不必把整张画面都抖动，力度和类型可以通过有限的方向与形状差异传达。

**设计建议**：普通攻击的挥空音与命中音分开；命中、防御、相消、霸体各自有一套反馈。重点先让接触位置、受击姿态和停顿吻合，再加震动和闪白。多段小命中不应每段都用最终重击的声量与震屏；大招收尾再形成峰值。

### 12. 表现需要可回收、可降级

死火`EffectManager.getEffectView`复用未激活实例，姿态位图缓存为残影/发光服务；`EffectCtrl.doEffectVO`还限制同一种效果的同帧触发数量。值得注意的是此限额判断在冻结、震动等处理之前，本项目若直接仿写就可能让特效限额改变交互。

街霸效果工作对象和纹理缓存有独立系统；本批定位了工作池与退出路径，未给出其资源峰值或平台帧率结论。

**设计建议**：千星版本把模拟事件与可丢弃的表现实例分开。规则照常执行，池耗尽时舍弃次要背景、残影与粒子，保留身体、关键火花和可读的受击。计算身体、独立特效、闪白、伙伴、HUD、缓冲和重叠面积的总预算，不能只报单个身体图的峰值。

## 建议推进顺序与可验收样例

这是**设计建议**，不是新增制作、发布或真机通过记录。角色动作仍由用户设计，Codex负责接入。

1. **先做交互可读性**：同一个既有轻击，分别演示挥空、打中、防住、霸体和护盾；对齐接触点、停顿、受击姿态、声音与推退。轻重两种对照即可验证反馈差异，不先扩大素材量。
2. **再核对连段权限**：选已有轻1→轻2→轻3→技能链，展示命中连上、防住可接、打空是否可接和输入过早/过晚。每个案例记录模拟拍和退出状态；对照注释与实际取消条件。
3. **补受击闭环**：站/蹲/空中受击、击飞、落地、倒地、起身；检查人体尺寸、方向、脚底、墙边位移和可行动时点。
4. **用一招验证华丽编排**：沿用户已提供的专属技能，将身体、独立效果、攻击对象、命中分支、镜头与收势放到一条可调时间线；末击强于中间击，落空与防住都有明确结束。
5. **最后扩展特殊交互**：投空/成对投技/拆投候选、相打、飞行物相消、特殊闪避和反击。是否采用新的Parry、破防或受击脱身规则由后续设计决定。

每批应分别记录：设计接受情况、模拟器结果、真机观察与推断。模拟器至少包含双方换位/镜像、墙边、同角色、同时出手、低显示频率、延迟回滚和连续多段；新表现事件必须证明不重复播放、不重复扣血、不滞留锁定和不越过图元预算。具体帧数与数值不能从参考游戏直接移植。

## 后续研究缺口

- 死火：完整FLA/XFL时间轴、典型角色逐帧招式、效果资源配置和音频观感尚未核验；本批无法报告某角色每招的准确帧表与技能全分支。
- 街霸：已经有仓库主代码归档，依赖子模块和运行用的原游戏数据未补齐；逐角色全部取消例外、浮空规则、每种投射物与效果池峰值仍需继续展开，不能将目录索引当完成清单。
- 两边：没有实际运行或录屏逐帧对照，停顿和镜头的视觉节奏仍需观察。
- 本项目：表中的静态差异没有形成复现测试，本批不关闭现有美术、性能或真机待验项。

本批产物是覆盖全战斗表现系统的源码研究与定位资料；两款游戏的每一个角色、每一个动作和每一个资源逐项验收尚未完成。
