# 图元运行优化与更多动作的设计

更新：2026-10-03。参考技能：`%USERPROFILE%/.codex/skills/qx-pixel-load-budget/SKILL.md`及其`references/load-budget.md`；本项目实测优先于相邻项目归档数字。

同日新候选：[双人下一版说明](../outputs/duel-vnext/使用说明与节点改动.md)。人物总 40 关键姿势使用两个 2335 峰值池；头像、火鸟、三背景也分别按实例峰值共用池。新版本总常驻图片约 9600，背景与头像新增成本不能忽略。下方 4550 是旧四姿势基线，不是新版本全部图元数；两版均未以模拟器结果保证手机帧率。

## 当前成本

现有light数据每名角色4个关键姿势，姿势并非完整连续动画。每个角色共用2275图片图元池，合计4550，不是四姿势全部常驻。背景、容器和其他UI另计。

|角色|姿势1|姿势2|姿势3|姿势4|峰值|
|---|---:|---:|---:|---:|---:|
|刻晴|792|1141|1282|1368|1368|
|迪卢克|1854|2029|2272|2274|2274|

按角色峰值重建池，理论共3642图片；但最新Lua优化**没有重打GIA缩池**，实际常驻仍4550。四姿势全预建共13012图片，约为当前2.9倍，不能因为只显示一套就忽略其常驻成本。

旧updateSprite已有角色/姿势key缓存，同姿势不重写像素池。但每次换姿势仍遍历2275，逐个FindChild、SetVisible；有效图元再写位置、大小和颜色。单次大姿势切换可产生约9000次属性写入，另有查找。这是本次攻击卡顿的高成本候选，不等于已测得每个API耗时。

## 录像证据

详见`outputs/video-check/录像校验结论.md`。071109录像实际约5.79～22.13秒：PC Lua更新增加635，手机增加58；两端战斗网络帧增加159，约9.7帧/秒。PC观察点领先手机12帧并等待，PC回滚480、重算4342均未增加。

支持的结论：手机脚本/模拟推进低频、PC达到预测窗口后等待。攻击换姿势重写大量UI与“移动跳跃较顺、攻击更卡”相符。不能直接证明所有卡顿都由图元循环造成；投屏延迟、设备负载、API耗时仍需要独立测量。录屏FPS不等于Lua更新频率，更不等于模拟帧率。

## 已实现的第一轮优化

设备候选：`outputs/visual-cache/fighter_online_rollback_debug.lua`。

1. 缓存像素控件、角色渲染节点及HUD节点引用，后续直接使用。
2. 每个像素记录上次可见性、x/y、w/h、颜色；只写变化属性。隐藏后记录保留。
3. 换姿势只遍历max(新姿势数量,旧姿势数量)，初始化首次仍扫描全部现有池确保未使用图元隐藏。
4. 场景分组只在地图改变时刷新显隐。
5. 删除一次随后被updateSprite覆盖的旋转设置。
6. 每约一秒统计LuaHz、Pose、Writes，不逐帧打印。

这些缓存是渲染派生状态，不进入战斗快照。回滚后最终绘制对比当前实际显示缓存与最新战斗状态；不能把渲染缓存当作模拟状态恢复。

LuaHz是脚本dt累计得到的更新频率估计；Pose是统计窗口里两角色的换姿势次数；Writes只统计像素池属性写入，不代表全部UI调用。没有加入函数耗时测量，因此不能把Writes减少当作已证明的真机提速比例。

验证：双独立客户端470帧、96个场景对照，除诊断文本外场景节点一致；含轻重攻、跳跃、两端切角色、切地图、重开。战斗核心/回滚代码保持文本一致。`verification.json`中的deviceVerified=false；手机效果等待用户测试。

## 下一轮方案的取舍

|方案|收益|成本/边界|当前状态|
|---|---|---|---|
|角色独立峰值容量|减少常驻和遍历|需要重建GIA；角色切换后每个席位池须适应可选角色峰值|未实现|
|跨姿势图元匹配|让相同部位保持编号，扩大差量复用|需离线匹配，保护绘制顺序与遮挡；当前按索引缓存不等于匹配|未实现|
|身体/武器/特效分层|整体移动旋转只写父容器，局部动作少更新|刚性变换不能替代所有轮廓；层级及遮挡要验收|未实现|
|两套显示池交替|分散下个姿势准备成本|常驻增加，需提前准备并原子切换；隐藏不是零成本|未实现|
|全部姿势预加载|切换时减少属性重写|常驻、包体、布局树显著增加；更多帧会持续放大|不作为默认方案|
|减少图片矩形|降低常驻/更新/绘制潜在成本|无损合并优先；不能为数量擅自毁掉认可造型|候选|

池按“实例可使用的所有角色/姿势峰值”分配。当前两个席位都能切角色，因此不能简单永久把P1缩成刻晴1368而仍允许P1选择迪卢克；需要按选择装配或保留足够容量。共享帧表不等于共享同屏实例的显示控件。

## 推荐的长期结构

- 素材离线保存帧表、锚点、颜色槽、图元对应关系与遮挡信息。
- 战斗逻辑输出动作、动作时间、朝向、位置与判定；渲染选择对应美术帧。
- 每个可见角色有独立显示池，静态帧表可共享。角色父容器负责世界位移，局部层负责武器等变换。
- 美术可以跳过中间显示帧，但不能跳过战斗模拟、命中、输入或发射事件。回滚重算期间不重绘每个历史帧，最终绘制一次。
- 调度与预加载使用主线程Lua任务预算，不把分批执行描述为已经有后台线程。不能在屏幕上暴露半套更新姿势；显示池与准备池要区分。
- 资源统计按创建/隐藏/回收/销毁事件更新，不每帧遍历整棵图元树当管理器。

## 成本口径与验证

图片矩形数、总控件数、可见数、常驻池、属性写入量、重叠面积、包体分别统计。显示倍率不减少图元，降色不等于运行时自动降控件，少矩形可能增加重叠绘制。没有已核验的全场固定5000硬上限。

真机对照尽量同设备、同场景和同攻击序列，一次改变一个主要因素。检查待机、连续轻重攻、双方同时换姿势、换角色、倒地和重赛。保留完整素材作为基线，记录LuaHz/模拟帧增长/等待占比，并在API允许时增加绘制与换姿势耗时。模拟器只证明兼容和逻辑对照，不保证手机FPS。
