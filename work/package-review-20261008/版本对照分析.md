日期：2026-10-08。范围：用户提供的十个 ZIP，只读检查说明、完整性、素材统计与模块差异；未运行其中脚本、未修改游戏源代码、未导入或发布。

## 后续补充：V18 已定位（优先于下方早期缺口记录）

用户随后提供改动作系统前的 GF_Online_Repair_3e508011db14 Lua，并明确它就是 V18。读取实文件所得 SHA-256 为 b6623a610eb1596bf71ba6d7dba8c30e24492ee560138da6fea8b8b39c4be464，3029620 字节，与 r33 MERGE_REVIEW 声明的基线完全一致。逐模块对照与差异保存在 V18/。

**已核实：** V18→r33 的 gf_net 与 gf_transport 字节完全相同；gf_online 只有开局种子表达式变化。V18 与 r33 的 onConfirmed 事件处理和 netTick 确认快照回放路径也相同。因此，确认帧表现不是这两个版本的回归变化；早前 r31→r33 的该项变化不能作为 V18→r33 卡顿的主因证据。

**真正变化：** V18 在进入战斗前扩到 11000、之后每更新补 2 个至 15000；r33 进入战斗需求为 14000、按余量扩容，增长阶段每更新最多 64 个，紧急分配可能另加。V18 用旧姿势名称做预取并分批写入，r33 两角色使用新动画名称，仍沿用旧 NEXT 表，换帧时预算提高到 1600。r33 A.prepare 对新动画只准备 basic_0 即返回完成，其余新姿势首次读取时同步解码、16 位转换和坐标烘焙。

**用户真机反馈：** V18 分阶段加载后能够运行，体验更流畅；优化雷神与草神后，最后联机草神位置会停一下再前进。该反馈证明存在体验回退，不提供回调耗时或网络等待根因。

**待验证推断：** 首次移动尤其应检查动作解码；循环移动仍周期性卡顿则应检查每次切关键帧/补帧的整图写入，以及同帧扩池。完整动作闪白主要用于解释受击时负载，不能解释没有受击的纯移动卡顿。动态池也只有创建或回收实际发生时才可归因。渲染负载可能拖慢输入收发、放大相同回滚算法里的预测等待，但尚无真机日志证实。

当前建议首先只改变准备阶段和移动换帧调度，保留动作设计与模拟规则，分别对照首次/重复移动；再独立检查扩池和受击闪白。尚未实施修复或本轮动态验证。

## 源码核实

1. 所附后台补池联机版与 r33 的 gf_net 模块字节完全相同：delay=2、maxPredict=12；gf_online 仅种子计算表达式有差异。因此没有证据称 r33 相比该旧包换了回滚算法或缩小预测窗口。
2. r31 与 r33 的 gf_fview、gf_online、gf_transport 模块字节完全相同；gf_sim 只差一空行。r33 沿用了 r31 的人物绘制与战斗模拟，不是全面重写。
3. r31 的联机音效/特效由 onFrame 预测帧事件触发并去重；r33 改回 onConfirmed，保存快照事件、逐条回放确认帧表现。所附后台补池联机版也已经使用确认帧，故此项是 r31→r33 的差异，不是旧联机包→r33 的新增。
4. 两角色 r33 换姿势使用 back:step(1600)，旧联机版由战斗场景传入 520。r33 当前动作图均少于 1600，所以通常整张姿势在一次绘制中写完；1600 是预算上限，不是每帧固定写入量。
5. r33 A.prepare 对新动画只访问 basic_0 后就返回已完成；其他姿势首次访问 A.animation 时执行 decodeAll、16 位数值转换和坐标烘焙。相较旧联机版逐步准备十二姿势，新版本把部分首次准备成本移入使用时刻。r31 也已有该路径。
6. r33 A.silhouette 对这两人直接返回完整动作图；受击闪白遍历该图全部矩形并逐次改透明度。旧版用独立简化轮廓。r33 禁止这两人生成旧残影是减负措施，但没有消除完整闪白的负载。
7. r33 NEXT 预取表仍是 idle/walk1 等旧姿势名称，新角色姿势使用 basic_0、move_1 等名称；该预取表无法为这些新姿势提供对应预取。
8. r33 动态池基线 14000、上限 20000、余量小于 2000 时申请扩容；增长阶段每次 App:update 调两次 growImages，默认每次 32，即最多 64。紧急分配还有额外 64 的路径。旧后台补池版 growBackground 每次仅增加 2。此比较仅指战斗后台增长，不把加载幕下的前台批量混入。
9. r33 Bitmap:step 使用 ensure(stop)，已经按本批进度取得节点；早先对仓库 Opus 基线 ensure(n) 的问题不能直接套给这个交付包。

## 与卡顿有关的推断

- **优先检查：首次动作同步准备、频繁整帧写入、完整图闪白。** 新动画增加表现力，但更频繁换图和新增特效会增加回调尖峰；首次用招与第二次用招的差异可帮助隔离解码成本。
- **条件性风险：战斗扩池。** 若卡顿帧 created 上升，64 个原生控件的创建及层级更新是明确嫌疑；若 created 不变，就不能把这一帧归咎于扩池。
- **联机表现风险：确认事件成批抵达。** r33 逐条在同一次 netTick 播放新确认事件，可能出现反馈延后和集中爆发；这不等于人物位置也改成确认帧显示，人物最后仍绑定预测状态。
- **潜在放大链：** 本地回调变慢→输入发送/接收处理不均匀→预测窗口耗尽或帧优势等待→人物走走停停。代码允许这条路径，但没有真机日志证明已发生。

不能从上述静态证据给出卡顿百分比、FPS，或声称已确定 V18→V33 的根因。

## 建议的对照顺序（尚未实施）

1. 找到用户认可 V18 的精确文件，锁定哈希及匹配的服务端节点；相同两角色、场景、设备与网络对照 V18/r33。
2. 首次/重复出招、持续移动、连续受击、大招分别测回调间隔、UI 写入、创建量、预测领先帧、stalls、回滚次数及重算帧数。
3. 独立候选先只改准备阶段：当前对局所需动作、补帧、特效分批解码并预备显示容量，再开战。避免把所有角色所有资源全常驻。
4. 第二候选只替换轻量闪白轮廓，保留身体画面、命中逻辑与动作时间；核对受击卡顿。
5. 第三候选在经过峰值核算的预备池下，对照战斗扩容开/关或受控批量，不能仅关闭扩容而让池耗尽。
6. 联机单独对照本地动作/挥击及时表现与确认伤害/胜负事件，按唯一事件标识去重。防止单纯为了所有反馈一致而把全部即时反馈推迟到网络确认。
