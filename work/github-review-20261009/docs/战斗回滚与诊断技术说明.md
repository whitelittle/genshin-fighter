# 战斗、回滚与诊断技术点

更新：2026-10-03。实现源：`work/rollback-session.lua`、`work/fighter-rollback-build.mjs`及当前生成Lua。需要扩展战斗时同步更新状态保存、恢复和测试。

## 三种时钟与停顿

|概念|行为|典型诊断|
|---|---|---|
|战斗模拟帧|设计目标60Hz，推进人物/招式/回合等|模拟进度慢会拉长动作的真实耗时|
|命中冻结hitstop|命中4帧、防住2帧，暂时停止战斗动作，网络帧仍推进|短促打击停顿；不会因命中自动触发回滚|
|暂停预测|缺对方输入且已领先连续确认12帧时，停止推进模拟|“等待远端输入·暂停预测”|

4帧在60Hz时约67ms，在实际约10模拟帧/秒时可拉长到约400ms，还可能叠加等待与绘制阻塞。12帧只有在60Hz推进时才约200ms，不能拿固定200ms解释所有实机卡顿。

回滚是迟到输入与预测不一致后恢复旧状态重算，不是冻结帧的另一名称。当前未生成取消hitstop对照版；最新视觉优化保留其规则。

## 输入与回滚

本地输入排进下一网络帧，不等服务器确认才执行。缺远端帧时预测无新事件，已按住的方向与防御保持，攻击按下沿不重复触发。

每帧保存完整战斗状态：人物、招式及进度、输入保持/缓冲、搓招历史、回合与胜场、计时、能量、倒地/浮空等。执行顺序固定玩家1再玩家2；迟到输入修正最早错误帧，然后重演至当前帧。回滚只计算逻辑，最终渲染一次。

网络帧独立于回合tick，重开/换角色不重置该网络时钟。历史窗口120帧，预测上限12帧。不是原生GGPO库，是Lua输入日志与状态回滚实现。原理参考[GGPO](https://www.ggpo.net/)，具体能力以本代码为准。

## 发包与守卫

- 约每50ms尝试发批次，但发送只能在OnUpdate运行时发生；更新低频不能保证20次/秒。
- 每批最多24帧，包含起始帧、连续确认及原始字符串；保留未确认输入，乱序/重复可以包含仍缺的帧。
- 每帧事件以逗号隔开，帧之间以`|`隔开，无事件帧为`-`。空操作仍发送，并非只在玩家按键时发。
- 接收端检查参数、批次数量、事件及数值范围；Payload上限8192字节是当前代码限制，不能当作千星API官方最大长度。
- 事件允许列表包含方向、防御、跳跃、轻重击、屏幕点击、摇杆、角色、场景与重开。
- 待处理输入最多32条；长时间暂停仍累积输入可能触发INPUT_OVERFLOW。当前没有修复此队列溢出恢复，不能宣称已解决。
- 错误会锁定会话，收到更多包不保证自动恢复，重新启动测试用于清理。

键盘轻重攻绑定按键按下/松开，屏幕按钮绑定CursorClick。不能未经实测断言手机Click一定在按下还是松开触发；当前卡顿录像更多指向更新/模拟慢，不等于点击事件问题已排除。

## 更新积压

当前每次OnUpdate的累积时间上限0.1秒，最多推进6帧；暂停预测时清空累计时间。这限制单次负担，但设备更新间隔过长时会丢弃经过的时间，模拟无法维持60Hz。提高catch-up上限可能增加单次负担，不能先无限补帧；应先解决绘制/更新成本，再评估调度。

## 诊断读数

|读数|能证明什么|不能证明什么|
|---|---|---|
|Hello/Join调用|发送API被调用|服务端确实接收|
|席位回调次数与Slot|Seat回调执行及原始参数|Frames转发已通|
|收到|符合对方Slot的FramesOut回调计数|每个批次最终完全通过解码；须同时看错误|
|网络帧|本地已推进的单调网络时钟|当前是第几回合或引擎FPS|
|远端确认|连续已收到对方输入的帧号|对方收到本地输入|
|对方确认|对方确认收到本地输入的帧号|双方当前画面处在同一帧|
|回滚/重算帧|回滚次数/重演量|单次耗时；没有增长时不能把当前停顿归因于新增重算|
|LuaHz|约一秒窗口按dt估计更新次数|真实引擎、录屏FPS或函数耗时|
|Pose/Writes|窗口内换姿势次数/像素池属性写入量|全部UI调用与设备耗时|

画面文字约一秒刷新，单张图不能证明两端严格同帧。录像可变帧率抽样目标时间与实际解码时间可能不同；`outputs/video-check/metadata.json`保存实际时间。投屏另有显示延迟，不把投屏差值全部算作网络延迟。

使用每阶段汇总打印及持续画面诊断，避免一个短句建一个打印节点或逐包刷屏。客户端日志与服务端节点日志不是同一个来源。

## 尚缺的正式联机能力

会话ID及旧包隔离、真实身份校验、断线重连、失步哈希与恢复、共享暂停、选人准备与重赛协议未完成。浮点战斗在同一Lua模拟器内通过确定性对照，PC/手机跨平台长期一致性仍未证明。

若加入AI随机、演出阶段、配色选择、更多招式或队伍机制，要明确哪些是模拟状态、哪些是渲染派生状态，并补快照与回放验证。不能只同步人物位置就宣称完整回滚。

## 已有验证

`work/fighter-rollback-verify.mjs`覆盖实际战斗状态、迟到/乱序/重复/丢包重传、与离线重算一致、超必杀、预测上限和非法输入拒绝、双客户端UI。探针版验证回调与断开服务器时持续提示。绘制优化版验证96个场景对照。各verification明确simulator/device边界。

实机已有能对战的证据，同时存在明显卡顿；两端某时刻能量或姿态不同可来自预测帧差，既不能立即认定永久失步，也不能据此宣布确定性通过。需要相同确认帧状态比较或后续哈希机制。

## 脚本生命周期与导入兼容经验

- 每名玩家需要自己的本地客户端界面和Lua实例；别让单人脚本与双人脚本同时绑定运行。玩家、客户端UI容器、官方服务端节点宿主属于不同层。
- 当前脚本OnStart先注册Seat、Joined、FramesOut回调，再发送Hello；重构时保持此先后关系，防止首次回包早于回调注册。
- 界面模板导入、客户端层级、实例创建/激活、脚本映射与生命周期须分层排查。客户端控件数量0或层级空是Lua运行之前的问题，修改seat或模板数字不会恢复丢失层级。
- 当前GIA预置图元，Lua不需要手填动态图元模板索引。导出编号可能被导入器重分配；服务端显示节点应选择当前导入实际生成的模板引用。
- 保持FighterDemo及人物Art/Sprite/P1…的名称层级，现有FindChild依赖它们；不能把数字为P1的图片控件与实体变量P1混为一谈。
- 当前设备Lua采用ASCII文本、无BOM、LF，中文通过UTF-8字节十进制转义输出，中文源稿另存。不要随手换编码而跳过真机启动验证。
- OnInit/OnStart/OnUpdate有错误捕获与可见诊断；无脚本时静态提示和脚本启动后的诊断有不同意义。黑屏先确认在哪一层失败，不直接假设网络故障。
- 脚本映射路径`lua/fighter_online_rollback_debug.lua`与导出文件实际位置不同。覆盖时确认修改的是当前绑定脚本，而非另一个历史资源或同名旧模板。

原始空层级导入修订见`导入空层级修订说明.md`。当时重排控件/脚本编号、重建资源引用、独立命名与脚本路径是兼容处理；多项一起改动，没有证明其中哪一项是唯一根因。不能将那批具体导出编号写成平台固定要求。
