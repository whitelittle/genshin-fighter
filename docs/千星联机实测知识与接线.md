# 千星联机实测知识与当前接线

更新：2026-10-03。适用：当前light素材的Lua回滚诊断/绘制优化版本。官方服务端节点图由用户手动制作，未作为本地自动生成资产保存。

同日后续：[双人下一版候选接线](../outputs/duel-vnext/使用说明与节点改动.md)增加 `FighterSelect/FighterSelectOut` 六参数及 `FighterFrames/FighterFramesOut` 第五参数 Epoch。Seat 不自动 Join，双方准备才开战；新流程、旧包隔离已模拟器验证，尚未经用户真机接线。下方为旧版实机知识，不能把新参数误说为已经实机验证。

## 实体、GUID与列表的区别

- GUID是场景放置实体的标识；动态创建实体可能为0。不是用户UID，也不能把运行时实体编号当作GUID。
- 本关卡共享变量实体使用GUID **1077936129**。这是用户当前关卡的配置，不是千星平台通用玩家GUID。
- 节点调试观察到在场玩家列表`[3,5]`，P1/P2分别可为实体3/5。这些是本次运行实例，不可硬编码到下一次。
- `获取在场玩家实体列表`提供玩家实体。玩家逻辑实体与可见角色实体是不同概念；目标客户端玩家应使用实际玩家实体，不默认使用角色或UI容器。
- 官方节点`获取列表对应值`序号从**0**开始：两人取0、1。Lua信号参数数组使用**1**开始：Slot取`params[1]`。两种索引不能混淆。
- `获取自身实体`取节点图挂载的实体。若图挂在共享公共实体，它是公共实体；挂在玩家上则是该玩家。读取变量与写变量必须使用相同的目标实体。
- 监听信号的“事件源实体”和“信号来源实体”是否能直接用作实际玩家身份，本次没有得到普适结论。不要简单把所有来源端口替换为事件源，也不要声称来源必然是容器。

官方依据：[基础概念](https://act.mihoyo.com/ys/ugc/tutorial/detail/mhk23ora1wom)、[玩家](https://act.mihoyo.com/ys/ugc/tutorial/detail/mhctmgi51lpo)、[服务端查询节点](https://act.mihoyo.com/ys/ugc/tutorial/detail/mhwbqlrw655q)。本地基础概念摘录见`work/官方-基础概念-GUID核验.md`。固定保留GUID指代P1/P2的说法本次未核验，不作为实现依据。

## 当前可工作的最小节点图

推荐单个公共实体运行转发图；P1/P2是实体变量，Started是布尔默认假。图中通过自身实体读写变量的前提是该自身就是变量宿主。若使用GUID查询宿主，各处须一致。不要同时启用旧图与新图。

### Hello：玩家列表分配席位

```text
监听 FighterHello
  → 在场玩家列表长度 >= 2
  → 设置 P1 = 列表[0]
  → 设置 P2 = 列表[1]
  → 向列表[0]发送 FighterSeat，Slot=1
  → 向列表[1]发送 FighterSeat，Slot=2
  → 一条汇总打印
```

此阶段为诊断简化方案，没有IsInit/P1Assigned/P2Assigned门槛。重复Hello仍能发回席位。用户重建此路径后两端席位回调成功，P2开始调用Join。多处同时变动，不能把此前失败唯一归因于某个端口。

列表顺序不应当作房主身份或稳定席位的长期保证；正式版需要会话内锁定名单、退出处理和身份验证。本方案适用两人测试。

### Join：回开战通知

```text
监听 FighterJoin
  → 在场玩家列表长度 >= 2
  → 设置 Started = 真
  → 向P1发送 FighterJoined（无参数）
  → 向P2发送 FighterJoined（无参数）
  → 一条汇总打印
```

当前Lua只有席位2自动发送Join，因此P1的Join调用为0是正常的。客户端已开战后会忽略重复Joined，服务端仍应允许重试获得回包；不要用Started已真挡掉所有回包。正式版应区分“只初始化一次”和“重复发送确认”，并增加双方准备。

### Frames：输入双向转发

```text
监听 FighterFrames
  → Started 为真
  → Slot == 1：向P2发送 FighterFramesOut
  → 否则再判断 Slot == 2：向P1发送 FighterFramesOut
```

|顺序|参数|类型|要求|
|---|---|---|---|
|1|Slot|整数|1或2，原样转发|
|2|FirstFrame|整数|批次起始网络帧，不能填常量|
|3|AckFrame|整数|已连续收到的对方输入帧，原样转发|
|4|Payload|字符串|保留完整输入批次，不拆、不加前缀|

发送信号大小写为`FighterFramesOut`。目标变量从同一公共宿主读取。客户端检查回包Slot应为对方席位，并由Lua处理乱序、重复和重传；节点不要自行按到达顺序丢旧批次。

此诊断图按Slot路由，没有实际发送者身份校验，不是正式防作弊方案。后续须核验真实身份，再确认身份与席位对应。

## 真机失败经验

|现象/误区|本次经验|
|---|---|
|两人列表取1、2|索引2越界；应取0、1。长度不足时索引1也越界|
|P2设置成功但回包无效|检查变量值输入是否漏接，目标实体与变量值是否接反|
|刚设置P2，读取疑似不是同一人|实际截图自身实体5、读P2也为5，不能继续假定变量丢失；沿发送与回调继续查|
|两次连续发送是否互相覆盖|后续相同连续发送结构成功，不能认定连续发两次是根因|
|发送节点后打印“完成”|官方概念说明节点执行失败未必停止后续流程，打印只证明执行到此，不证明客户端收到|
|IsInit已真后完全禁止重试|首次回包失败会让流程无法恢复；状态初始化与确认重发须分开|
|脚本统计Hello/Join增加|只是调用发送API，不证明服务端收到|
|手机日志无法从PC日志面板找到|使用客户端画面持久诊断，不依赖不确定的2P日志入口|
|已开战但角色不动|两端收到输入为0，网络帧停12，说明输入转发未通|
|手机玩家静止会不会不发包|空操作帧仍记录并发送；停止脚本更新或送包才会让另一端等|

客户端指南中的“服务端发送信号联机延迟最低100ms”是延迟描述，不是每100ms只能发送一次的频率规则。依据：[客户端脚本指南](https://act.mihoyo.com/ys/ugc/tutorial/detail/mhbgxf0nynww)及相邻资料库快照。

## 验证边界与后续

已实测席位、开战、双向输入能到达且能够对战；仍有攻击卡顿。未完成跨CPU长期一致性、失步恢复、会话隔离、断线重连、正式身份验证、共享暂停、正式选人准备协议。

每次换Lua/节点图后两端退出重进，清理共享变量；当前协议没有会话号，旧包与新局混用有风险。正式重赛设计不能只清零网络帧。

历史`FighterInput/FighterInputOut`和`FighterState/FighterStateOut`属于早期P1主持快照方案，不能与Frames回滚协议混用。
